Preparación antes de la exposición

  1. Abre el PowerPoint y activa la vista del moderador para consultar las notas.
  2. Abre el PDF local y comprueba el proyector y la legibilidad.
  3. Inicia sesión como administrador y como empleado en perfiles o ventanas privadas diferentes. Comprueba el rol antes de cada demostración.
  4. Prepara un registro de exposición, un PDF de soporte y una quincena finalizada. Evita mostrar contraseñas y documentos personales durante la proyección.
  5. Ensaya una vez con cronómetro. Al llegar al minuto 11 deberías estar terminando la descarga del desprendible y pasando a las pruebas.
  6. Si falla internet, continúa con el PDF y explica el recorrido previsto. La aplicación requiere conexión y no forma parte del respaldo sin internet.

Demostración práctica

  1. Administrador: abre Empleados, explica los campos de alta y consulta el perfil preparado. Si creas un registro durante el ensayo, usa el entorno autorizado.
  2. Empleado: abre Documentos, muestra los datos automáticos y compara un permiso con fecha frente a un ajuste de nómina con N/A. Explica el soporte PDF opcional y consulta el historial.
  3. Seguimiento: muestra una solicitud preparada, la decisión administrativa y el estado conservado al recargar como empleado.
  4. Nómina: descarga una quincena finalizada. En el ejemplo de supervisor, explica el neto mensual de $3.200.000 y el neto quincenal de $1.600.000. Las tasas del comprobante corresponden a la configuración del proyecto y la aplicación no confirma pagos bancarios.

Guion para practicar

1. SESHA APP

Soy Alexander Rivera Sánchez, aprendiz de Análisis y Desarrollo de Software de la ficha 3186701. Presento SESHA APP, una aplicación para centralizar información laboral, documentos y solicitudes de empleados de una empresa de seguridad. Mostraré el proceso de construcción, las decisiones técnicas y una demostración funcional.

2. Consulta de información y seguimiento de trámites

El problema que aborda el proyecto es la consulta de información laboral y el seguimiento de los trámites internos. El empleado necesita saber qué información tiene registrada, obtener documentos y conocer el estado de sus solicitudes. El administrador necesita identificar a la persona y conservar una decisión consultable. Este planteamiento se deriva del alcance implementado. No presento cifras de ahorro ni entrevistas a una empresa que no estén documentadas.

3. Objetivo y alcance

El objetivo general es centralizar estos procesos en una aplicación web con identidad y permisos controlados en el servidor. El empleado opera sobre su propia información. El administrador gestiona perfiles y revisa trámites. El alcance incluye documentos PDF, constancias, comprobantes quincenales y solicitudes. Una aprobación de ajuste no ejecuta una transferencia bancaria ni liquida automáticamente una novedad salarial.

4. Requisitos verificables

Esta matriz sintetiza los requisitos de la versión que estoy sustentando. La reconstruí a partir del comportamiento del código y de los casos ejecutados para hacer explícita su trazabilidad. No la presento como un acta histórica de requisitos firmada por un cliente. Cada historia tiene una condición comprobable. Los requisitos no funcionales se concretan en autorización, validación de entradas, almacenamiento persistente y umbrales de rendimiento definidos para el ensayo local.

5. Construcción iterativa y aporte individual

La solución evolucionó por iteraciones verificables en el repositorio y en las bitácoras. Las capturas de julio y agosto corresponden a Jest. La versión actual usa Vitest y pruebas HTTP. Mi aporte en esta sustentación integra implementación, conexión con MongoDB, controles de acceso, pruebas y documentación. Hablo de construcción iterativa porque existen correcciones y validaciones sucesivas. No afirmo haber aplicado un marco Scrum formal ni tener actas de sprints que no estén disponibles.

6. Arquitectura de la solución

La arquitectura es un monolito modular con responsabilidades separadas. React y Vite resuelven la presentación. Express ejecuta las reglas de negocio en una función de Vercel. Mongoose comunica la API con MongoDB Atlas. El navegador utiliza la API del mismo dominio. Los permisos pertenecen al servidor y la base conserva los registros. Esta escala no exige separar el sistema en microservicios. El diagrama representa el estado implementado y permanece editable.

7. Modelo lógico de datos

La cuenta User guarda autenticación y rol. Su colección histórica se llama empleados. El perfil laboral Empleado usa perfiles_empleados y referencia la cuenta mediante user, con índice único. Documento referencia al propietario y contiene el PDF. Solicitud también referencia al propietario y puede asociar un documento. Cada solicitud nueva conserva una copia de los datos laborales del momento de radicación. Las fechas y el estado permanecen en la base. El modelo es una síntesis de los esquemas actuales, no una captura de Atlas con datos personales.

8. Casos de uso por rol

Este diagrama resume los casos de uso principales. El empleado consulta su perfil, obtiene sus documentos y radica solicitudes. El administrador gestiona perfiles y resuelve los trámites. La autenticación es una precondición de los módulos privados. El control de propietario restringe al empleado a sus registros. Un cargo laboral como coordinador o administrativo no convierte la cuenta en administrador.

9. Diseño de interfaz y navegación

La interfaz organiza la navegación por tareas y por rol. Esta imagen es una captura real de referencia del formulario vacío del 14 de noviembre. No la presento como una revisión visual nueva del navegador. El mapa de la derecha describe los módulos actuales. La interfaz usa controles con etiquetas, mensajes de error y confirmación posterior a la respuesta del servidor. El manual explica los formularios recientes con tablas y pasos de uso.

10. Controles de seguridad

JWT identifica la sesión y viaja en una cookie HttpOnly, Secure y SameSite Strict. Las escrituras con cookie requieren CSRF. La API recupera la cuenta y verifica su estado y versión de sesión. Las contraseñas usan bcrypt de coste 12, y el cambio de clave invalida las sesiones anteriores. El servidor valida campos y restringe archivos a PDF de 3 MB. La API limita solicitudes e intentos de autenticación. Los secretos permanecen en configuración privada y nunca deben aparecer en las diapositivas ni durante la demostración.

11. Demostración del administrador

Cambio al navegador con la sesión administrativa ya iniciada. Abro Empleados y el formulario Nuevo empleado. Explico que el nombre puede repetirse, pero correo y documento deben ser únicos. La opción de crear cuenta exige una clave inicial oculta. Para demostrar un guardado uso un registro de exposición preparado en el entorno autorizado, sin mostrar credenciales ni datos privados de personas. La cuenta y el perfil se crean en una transacción. Si solo explico el formulario, cancelo el alta y abro el perfil preparado para mostrar la persistencia al recargar. Este segmento se ensaya antes de la exposición.

12. Demostración del empleado

Uso otra ventana del navegador con una sesión de empleado preparada, para evitar confundir los roles. Abro Documentos y muestro los datos que vienen del perfil. Selecciono un permiso y una fecha válida. Después cambio a Ajuste de nómina y señalo que la fecha presenta N/A. Escribo un motivo de exposición, uso Examinar si existe un PDF de soporte preparado y envío en el entorno autorizado. Reviso la confirmación y el historial. Vuelvo a la sesión administrativa, localizo el trámite y registro una decisión. Al recargar como empleado se conserva el estado. La cuenta de empleado no dispone del control de aprobación.

13. Demostración del desprendible quincenal

En Documentos selecciono un mes y una quincena finalizada y descargo el desprendible. El ejemplo corresponde a un supervisor con neto mensual de 3.200.000 y neto quincenal de 1.600.000. Para conservarlo, el sistema calcula un devengado de 1.666.666 y descuenta 33.333 por salud y 33.333 por pensión. Las tasas del 2 % cada una son la configuración solicitada para este comprobante y no sustituyen una liquidación legal de aportes. Bancolombia es el medio informado por SESHA. La aplicación no confirma una transferencia ni incorpora automáticamente recargos o novedades. No muestro el documento personal de un empleado durante la exposición.

14. 196 comprobaciones funcionales aprobadas

La campaña repitió 105 pruebas de backend, 33 de interfaz y 58 verificaciones HTTP, para 196 comprobaciones locales aprobadas. Las 15 verificaciones de producción se presentan separadas. Los casos abarcan rol, propietario, transacciones, solicitudes, N/A, PDF y nómina. Conservé los intentos iniciales: una prueba de tasa dependía de cruzar una ventana temporal y una ampliación HTTP utilizó mal un Buffer de prueba. Corregí el ensayo y repetí la suite completa correspondiente. El límite de producción no cambió. Los informes detallan cada caso y sus resultados.

15. 100 solicitudes/s confirmadas en el entorno local

k6 confirmó 100 solicitudes por segundo durante un minuto, con 6.001 respuestas, p95 de 66,1 milisegundos y cero errores o iteraciones descartadas. p95 significa que el 95 % de las respuestas quedó por debajo de ese tiempo. El gráfico compara escalones de 25 segundos y muestra el umbral de 500 milisegundos. Las tasas de 125, 150 y 200 quedaron fuera de umbral. El login también falló a 4 por segundo por latencia. Conservé las cuatro etapas fallidas. La mezcla incorpora las rutas nuevas de solicitudes y nómina. El generador, la API y MongoDB compartieron el equipo local. No extrapolo estas cifras a Vercel, Atlas o usuarios simultáneos.

16. Seguridad evaluada con ZAP

ZAP local registró cuatro clases informativas y ninguna alta, media o baja. En Vercel quedó una alerta media Cross-Domain Misconfiguration por CORS en recursos públicos y cuatro informativas. Conservo la clasificación automática en el informe. El contraste verificó que una API con sesión rechazara un origen ajeno con 403 y el acceso anónimo con 401. También comprobó perfiles distintos, el formulario propio y la nómina del empleado. No observé exposición privada en estas lecturas. Esto no equivale a certificar ausencia de vulnerabilidades. El escaneo activo usó dos reglas sobre paginación GET, con un hilo y pausa de 1.500 ms. Los conteos de negocio no cambiaron.

17. Entrega, despliegue y documentación

La aplicación está publicada en Vercel y usa MongoDB Atlas. GitHub conserva el código y su historial. La integración continua ejecuta lint, pruebas, compilación, auditoría de dependencias y búsqueda de secretos. Pages reúne los seis PDF actualizados: informe funcional, k6, ZAP local, ZAP Vercel, manual de usuario e informe técnico. El README incluye instalación y despliegue, con nombres de variables y sin valores de credenciales. Las copias descargadas de Pages se compararon byte a byte con los PDF locales.

18. Conclusiones y siguientes mejoras

El resultado es una solución funcional con persistencia, roles diferenciados y documentos vinculados al empleado. Los requisitos principales tienen pruebas y la entrega dispone de manuales e informes verificables. El siguiente trabajo es incorporar novedades e historial salarial, evaluar almacenamiento de objetos para superar el alcance actual de PDF y completar revisión visual y medición de producción. Estoy preparado para ampliar las decisiones técnicas o mostrar un caso específico de la aplicación.
